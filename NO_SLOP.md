# NO_SLOP.md — code-review standard for this MicroZig fork

> **What this is:** the quality bar every change to this fork is reviewed against, whether a person, an LLM, or both wrote it. It is distilled from Andrew Kelley's own writing, the official Zig docs and `zig zen`, and MicroZig's own `ARCHITECTURE.md`, then adapted for firmware: code that runs on bare metal, talks to hardware through memory-mapped registers, and shares state with interrupt handlers.
>
> This fork's [Code of Conduct](CODE_OF_CONDUCT.md) lets contributors use any tools they like, LLMs included. This document is the other half of that deal: **the tool is your choice; the bar is not.** If you use an LLM, point it at this file.

---

## 0. How to read this guide

There are **two different things** people mean by "Kelley's view on AI code," and a reviewer that conflates them will be wrong:

1. **The idiomatic-Zig bar** (§2–§5) — a *stable, long-standing* set of design tenets from Kelley's writing and the official docs, plus the embedded rules MicroZig's architecture demands. This is what you enforce, *regardless of who or what wrote the code*.

2. **The "AI slop" stance** (§6) — Kelley's *policy and rhetoric* about AI-generated **contributions to the Zig project**, motivated by reviewer-time economics, mentorship, and a **process** claim ("unreviewed code shipped on the strength of a test suite is not good enough"). This fork does not adopt the policy, but it does adopt the process claim: nothing ships on "the tests pass."

> **Load-bearing nuance:** frame every finding around **code properties**, never authorship. "This read-modify-write races the UART IRQ" is a finding. "This looks AI-generated" is not.

**The one-sentence bar** (Kelley's words): *"The bar that I want to hold software to is uncompromising perfection"* — explicitly rejecting *"works surprisingly well"* and *"the test suite catches everything"* as sufficient. Firmware raises the stakes: a bug here can brick a board, hang a robot mid-motion, or corrupt flash.

## 1. The Zen of Zig — the values every rule descends from

The lines of `zig zen` that most directly drive review:

- **Communicate intent precisely.**
- **Favor reading code over writing code.**
- **Only one obvious way to do things.**
- **Runtime crashes are better than bugs.** / **Compile errors are better than runtime crashes.**
- **Edge cases matter.**
- **Reduce the amount one must remember.**
- **Resource allocation may fail; resource deallocation must succeed.**
- **Memory is a resource.**

Kelley's ranked priorities (*Introduction to the Zig Programming Language*): **Pragmatism → Optimal (perf ≥ C) → Safety → Readability**, with *"the most natural way to write a program should result in top-of-the-line runtime performance."* On a microcontroller with a few hundred KiB of RAM, "optimal" includes **code size** and **RAM footprint**, not just speed.

## 2. Reviewer rubric — the hard rules (flag every violation)

A violation here is almost always a real defect, not a style nit.

### 2.1 Hardware access goes through `Mmio`

- **Rule:** register access goes through the generated `Mmio` types (`core/src/mmio.zig`): `read()`, `write()`, `modify()`, `modify_one()`, `toggle()`. `ARCHITECTURE.md` states this directly.
- **Flag:** raw `@ptrFromInt` to a peripheral address, or a non-`volatile` pointer to hardware. The compiler may cache, reorder, or delete such accesses. It will look correct in Debug and break under `ReleaseSmall`.
- **Flag:** code that reads a register "to check" and then writes it based on the stale value when the hardware can change it in between (status/flag registers, FIFOs).
- **Flag:** write-1-to-clear or read-to-clear registers handled with `modify()`. A read-modify-write on a W1C register clears every *other* pending flag that happened to be set. Use `write()` with only the intended bit.

### 2.2 Generated code is not edited

- **Rule:** register definitions are generated by `regz` from vendor SVD/ATDF files plus patches. `ARCHITECTURE.md`: *don't edit generated register code, and don't edit the svd files. Add patches in the port's `patches/` directory.*
- **Flag:** any hand edit to generated register output or to a vendored SVD/ATDF file. The fix is a patch, so the correction survives regeneration.

### 2.3 Interrupt safety

Interrupts are the hidden concurrency in firmware. Every piece of state touched from both an ISR and the main loop (or from both cores, on multicore parts) is shared state.

- **Rule:** shared state is protected by a critical section (`microzig.interrupt.enter_critical_section()`), a `microzig.interrupt.Mutex`, or an atomic. Pick one and make it visible at the access site.
- **Flag:** a `CriticalSection` without `defer cs.leave()` **immediately after** `enter_critical_section()`. A missed `leave()` on an early return or error path leaves interrupts disabled forever. That is the firmware version of a leak, and it hangs the device. (`leave()` restores the *previous* state, so nesting is safe; skipping it is not.)
- **Flag:** `Mmio.modify()` on a register that an ISR also modifies, without a critical section. `modify()` is read, change, write. An interrupt between the read and the write loses the ISR's update.
- **Flag:** a multi-byte variable (a `u64` tick count, a struct) read in the main loop while an ISR writes it, with no protection. On a 32-bit core that read can tear.
- **Flag:** blocking work inside an ISR: busy-wait sleeps, `std.log` to a slow UART, flash erase, unbounded loops. ISRs do the minimum and hand off.
- **Flag:** a lock taken in the main loop that an ISR also takes. If the ISR fires while the main loop holds it, the device deadlocks.

### 2.4 Explicit allocators — and usually, no allocation at all

- **Rule:** most firmware should not allocate at runtime. Prefer static buffers, caller-provided buffers, and comptime-sized arrays. When allocation is genuinely needed, the function **takes an `Allocator` parameter**. There are no hidden allocations.
- **Flag:** library code (`core/`, `drivers/`, a port's HAL) that reaches for a global or file-scope allocator. `ARCHITECTURE.md`: *No global mutable state in libraries. Embedded code uses explicit initialization and passed handles.*
- **Flag:** an allocation whose free is not paired with `defer`/`errdefer` immediately after it, or a missing `errdefer` on a partial-construction path.
- **Ownership:** every allocator-taking function is one of: **self-freeing** (frees all scratch; only the return value escapes), **owned-result** (caller calls `deinit`), or **caller-buffer** (takes a `[]u8`, allocates nothing). Caller-buffer is preferred on-target. A function that allocates scratch and relies on the caller passing an arena is a leak under any other allocator.
- **Host tools** (`tools/`: `regz`, `uf2`, `esp-image`, the linter) run on a desktop. They allocate normally, but the same ownership rules apply, and their tests should use `std.testing.allocator` directly, with leak detection on (an arena wrapped around it hides leaks).

### 2.5 Errors are values — none may be silently ignored

- **Rule:** every error union is handled with `try`, `catch`, an explicit switch, or a `catch unreachable` that is genuinely provable.
- **Flag:** `catch unreachable` / `catch {}` used to *silence* an error that can actually occur. In firmware, "can actually occur" includes hardware: a NACK on I²C, a timeout waiting for a peripheral, a sensor that isn't plugged in. Those are runtime conditions, not invariants.
- **Flag:** `catch |err| {}` that swallows without logging, propagating, or handling.
- **Flag:** over-broad `anyerror` where a minimal error set is knowable. Driver and HAL error sets should name their failures (`error{Timeout, Nack}`), so callers can switch on them.
- **Flag:** discarding a returned error union with `_ =`.

### 2.6 Hardware edge cases and timeouts

- **Rule:** every wait on hardware is bounded. A `while (!reg.read().READY) {}` with no deadline hangs the device forever when the peripheral is unclocked, misconfigured, or absent.
- **Flag:** an unbounded poll loop in HAL or driver code, unless the datasheet guarantees completion in bounded time and a comment cites it.
- **Flag:** clock, baud, or divider arithmetic that can overflow, truncate silently, or divide by zero for some valid configuration. Prefer computing and checking it at comptime when the inputs are comptime-known.
- **Flag:** register sequences that contradict the datasheet's required order (for example, enabling a peripheral before its clock), or that skip a documented settle delay. Cite the datasheet section in the fix.

### 2.7 Correctness > passing tests

- **Rule:** a green CI run is **not** proof of correctness. Most of this repo's CI only *builds* firmware; it cannot see a timing bug, a W1C mistake, or a race with an ISR.
- **Flag:** logic that "passes the tests" but is unsound on unexercised edge cases — *edge cases matter*.
- **Flag:** assertion abuse — `assert`/`unreachable` used to paper over a state that can happen. On `ReleaseSmall`/`ReleaseFast`, `unreachable` is undefined behaviour, not a crash.
- **Reviewer behavior:** reason about *what inputs, states, or interrupt timings break this*. Say which evidence a claim rests on: "builds for all ports", "unit-tested", "ran on hardware (board name)". These are different, and a PR description must not blur them.

### 2.8 comptime: used heavily here, so used carefully

Kelley warns about *"comptime abuse"* and its compile-time cost. MicroZig is a legitimate heavy user of comptime: `microzig.config` is a comptime struct injected by the build, HALs select peripheral implementations at comptime, pin and clock configuration is resolved at comptime, and `Mmio` itself is a comptime-generated type. **Do not flag that design.**

- **Do flag:** comptime machinery where a plain function would be clearer, or `anytype` parameters where the accepted type is actually one concrete type or a small explicit interface (for drivers, `drivers/src/base/`).
- **Do flag:** pushing work to runtime that could be checked at comptime. A pin that doesn't support a function, or an impossible clock configuration, should be a `@compileError`, not a runtime failure. *Compile errors are better than runtime crashes.*
- **Weigh:** build time. `regz` output for a large chip is big. Gratuitous comptime on top of it slows every build for every port.

## 3. Architectural invariants (from `ARCHITECTURE.md`)

These are what keep MicroZig portable. A change that breaks one is a design defect, even if it compiles.

- **Drivers never import port-specific code.** They work only through the base interfaces in `drivers/src/base/`.
- **Ports are self-contained.**
- **Core is port-agnostic.** It receives chip, HAL, and board configuration through comptime imports injected by the build system.
- **Register definitions are generated** (§2.2).
- **No global mutable state in libraries** (§2.4), except the narrow context-free C
  callback ABI exception in `ARCHITECTURE.md`: a port HAL may keep one synchronized
  routing pointer for a singleton peripheral. Explicit initialization, a stationary
  caller-owned handle holding queues and operation state, second-owner rejection, and
  teardown that prevents old completions reaching a new owner are required. ESP-NOW
  and IEEE 802.15.4 radio callbacks use this pattern. Global allocators and general
  library state remain prohibited.
- **Memory regions are the port's responsibility.** Core and drivers don't assume a memory layout.

## 4. Readability and "one obvious way"

Weigh these as strong preferences; a violation is a smell, not always a bug.

- **Prefer the canonical construct.** If core, the HAL, or the stdlib already provides it (a `Mmio` method, `microzig.interrupt.Mutex`, `std.ArrayList`, `std.fmt`), don't hand-roll a variant.
- **Write for the reader.** Register setup should read like the datasheet sequence it implements. Name the fields; avoid magic masks and shifts when the generated register type has named fields.
- **Communicate intent precisely.** Prefer narrow types (`u4` for a 4-bit field, an `enum` for a mode) over `u32`-for-everything.
- **Reduce what one must remember.** Flag invariants maintained across distant code with nothing local to signal them, such as "this must be called before the clock is changed."
- **No dead or speculative generality.** Unused parameters, one-caller abstractions, configuration knobs nothing uses.
- **Doc comments are accurate.** A doc comment that describes behaviour the code doesn't implement is a bug-class finding, not a nit.

### Performance and footprint

Kelley's data-oriented-design advice (*make the struct you have the most of smaller; avoid cache misses*) applies here mostly as **RAM and flash footprint**. On these targets the binding constraint is usually RAM and flash size rather than cache misses. Flag a struct that is instantiated many times and obviously bloated by padding or rarely-used fields, or a buffer sized far beyond its need. Don't demand DoD on one-shot configuration structs. Bring a measurement (`size` output, a map file), not an assertion.

## 5. What NOT to flag — style is deliberately un-enforced

Kelley (as `andrewrk`) has stated officially:

> *"Zig will not enforce identifier naming conventions according to any style. The 'style guide' will always be merely offered as a point of commonality..."*

> *"Errors such as unused variables or misleading indentation are about **catching bugs**, not enforcing any particular style."*

- **MicroZig's naming is snake_case functions, PascalCase types** (`ARCHITECTURE.md`), not the Zig style guide's camelCase functions. Consistency with the surrounding code is worth a *suggestion*. Never report naming as an error, and never "fix" existing snake_case to camelCase.
- **Formatting:** `zig fmt` owns it and CI checks it. Flag only *misleading* indentation.
- **DO treat as real:** unused variables/imports, shadowing, ignored errors, leaks, reachable `unreachable`.

**Calibration rule:** classify every finding as **bug-class** (enforce) or **style-class** (suggest, never block). Misfiling a style nit as a bug is itself a review defect.

## 6. The "AI slop" doctrine, and how this fork applies it

Kelley's most-quoted positions (from a ~May 2026 JetBrains podcast, his July 2026 Bun blog post, and Zig's Code of Conduct):

- **On value:** *"People are sending us contributions that have no value whatsoever. They have negative value, because they take review time away from the team."*
- **On the test-suite defense:** *"The argument for shipping all the million lines of unreviewed slop is that the test suite is good enough to catch everything. It's not sufficient to catch bugs in Zig code but it is sufficient to catch bugs in a million lines of unreviewed slop?"*
- **On the bar:** *"I'm always hearing people say that AI code works surprisingly well. But to me, that is not the bar... The bar that I want to hold software to is uncompromising perfection."*

This fork disagrees with banning the tool and agrees with the bar. What that means in practice:

1. **Review to "uncompromising perfection," not "CI is green."** Hunt races, unbounded waits, swallowed errors, and datasheet mismatches. Give concrete failure scenarios.
2. **Know the slop fingerprints** — the defects unreviewed generated firmware characteristically ships:
   - register addresses or bit positions that are *plausible* but not from the datasheet or the generated types (hallucinated hardware)
   - `catch unreachable` over I²C/SPI/UART calls that can fail on real hardware (§2.5)
   - unbounded `while (!ready) {}` polls (§2.6)
   - `enter_critical_section()` without an adjacent `defer leave()` (§2.3)
   - `modify()` on W1C registers (§2.1)
   - hand edits to generated register code instead of a patch (§2.2)
   - drivers that import a port's HAL directly (§3)
   - reimplementations of what core or the HAL already provides
   - doc comments describing behaviour the code doesn't have
3. **Large volume is its own risk.** A huge diff justified by "it builds" should be split and reviewed line by line.
4. **Judge the code, not the author.**
5. **Be precise.** Cite `file:line`, give the minimal fix, and cite the datasheet section for any hardware claim.

## 7. What the evidence does NOT support (don't overreach)

- ✗ *"Non-determinism is Kelley's single core objection to AI."* It is one of several (economics, mentorship, trust).
- ✗ *"AI can never write correct code"* as a universal law. His remarks target contributions to the Zig project and unreviewed bulk shipping.
- ✗ Treating naming or formatting conventions as enforceable rules (§5).

§2–§5 rest on primary sources (Kelley's blog, ziglang.org, the Zig issue tracker, the Zen, this repo's `ARCHITECTURE.md` and `core/src/`). §6's quotes rely on tech-press reporting of primary events and may evolve.

## 8. One-screen reviewer checklist

**Bug-class — enforce (block):**
- [ ] Register access through `Mmio`; no raw or non-volatile hardware pointers
- [ ] No `modify()` on write-1-to-clear / read-to-clear registers
- [ ] No hand edits to generated register code; corrections are patches
- [ ] State shared with an ISR or the other core is protected; `defer cs.leave()` directly after `enter_critical_section()`
- [ ] No blocking work in ISRs; no lock shared between ISR and main loop
- [ ] Every hardware wait is bounded, or cites the datasheet guarantee
- [ ] No runtime allocation on-target without reason; allocating fns take an `Allocator` and pair alloc/free
- [ ] No ignored or swallowed errors; hardware failures are errors, not `unreachable`
- [ ] Precise error sets; no reachable `unreachable`
- [ ] Architectural invariants hold (drivers port-agnostic, core port-agnostic, no global mutable state in libraries)
- [ ] Evidence class stated: built / unit-tested / ran on hardware

**Readability/idiom — suggest (don't block):**
- [ ] Canonical core/HAL/stdlib construct over a bespoke one
- [ ] Named register fields over magic masks; narrow types
- [ ] comptime/`anytype` justified; impossible configurations are compile errors
- [ ] Doc comments accurate

**Do NOT flag:**
- [ ] snake_case function names (this codebase's convention)
- [ ] Whitespace `zig fmt` owns (except *misleading* indentation)
- [ ] "This looks AI-written"
